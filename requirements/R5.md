# R5 · Per-account budget for an accounting period

## Agent-facing spec

### Business requirement

An account may carry a **budget** for a given accounting period. The budget caps the total debit amount that may be posted to that account across all transfers within that period.

- A budget is set for one account and one accounting period, and is expressed in the account's currency.
- When a transfer is committed, the current accounting period is determined (the period derived from the ledger's clock at that moment — the same rule used when closing periods). For every account the transfer touches, the budget for that account **in that period** is looked up:
  - If a budget exists, the sum of that account's debit legs in this transfer is added to the amount already debited to that account in that period. If the new total is greater than the budget, the **whole transfer** is rejected.
  - If no budget exists for that account in that period, that account is unlimited for that period.
- The amount already debited to an account in a period accumulates across transfers. A transfer in a later period starts from zero for that period.
- The cap is evaluated per account, not per transfer.
- A rejected transfer must leave no trace: no transaction is recorded and no account balance changes, and the period's accumulated debit amounts are unchanged.
- Budgets are part of the ledger's state and behave identically on every storage backend.

### Required public API

```java
// new type in com.yanimetaxas.bookkeeping.service
public interface BudgetService {
    void setBudget(String accountRef, String period, Money amount);
    Money getBudget(String accountRef, String period);      // null when no budget is set
    Money getBudgetUsed(String accountRef, String period);  // debit amount already posted in that period
}

// new type in com.yanimetaxas.bookkeeping.exception
public class BudgetExceededException extends BusinessException
```

The exception must expose the offending account reference and period through the constructor
`BudgetExceededException(String accountRef, String period)`.

The budget service must be reachable from a ledger and must reflect the ledger's current state.

### Acceptance criteria

1. A transfer that would push the period's accumulated debit for a budgeted account above its budget throws `BudgetExceededException`.
2. After such a rejection, no transaction was recorded, no balance changed, and `getBudgetUsed` is unchanged.
3. A transfer that brings the accumulated debit exactly to the budget is accepted.
4. An account with no budget for the current period is unlimited in that period.
5. The accumulated debit is per period: an amount debited in one period does not count against the budget of another period.
6. Several debit legs on the same account in one transfer are summed before the budget is checked.
7. The budget is evaluated independently per account: one account exceeding its budget rejects the transfer even when another touched account is within its budget.
8. `getBudget` returns the configured budget and `null` when none is set; `getBudgetUsed` returns the accumulated debit for the period.
9. Behaviour is identical on every storage backend — extend the existing cross-backend contract test to cover this.

## 中文说明（不给 Agent）

**业务场景**：项目预算控制 —— 「本月这个科目的支出上限是 X，超了就不许再记」。
这是把 R1 的「单笔限额」升级为「周期累计额度」，因此也把 R2 的「会计期间」概念真正用起来。

**为什么这条需求特别有价值**：这是**第 5 轮**需求，A 组此时已经累积了 R1–R4 的所有改动。
本需求要求**同时**用到：账户（账本上下文）、会计期间（R2 引入的状态）、期间累计金额（新的聚合查询）。
在 A 上，这三者分别散落在 memory/jdbc 两套后端、隐式 session、以及两套查询实现里；
到第 5 轮时，A 组的改动波及面会被前面几轮的架构债**放大**，而 B 组因为前几轮已经把规则收敛到单处，
本需求很可能只需在一处落地。这就是「架构劣化曲线」的拐点。

**依赖关系**：依赖 R2（会计期间）与 R1（账户扩展位）。
