# R2 · Closed accounting periods

## Agent-facing spec

### Business requirement

Every posting is attributed to an **accounting period**, derived from the clock the ledger was opened with. A period is identified by a string of the form `yyyy-MM` (for example `2026-01`).

- A period can be **closed**. Closing is a ledger-level operation and is visible to everyone using that ledger.
- While the ledger's **current** period is closed, committing a transfer is rejected with a dedicated exception.
- The current period is the period derived from the clock at the moment of the commit attempt.
- A rejected transfer must leave no trace: no transaction is recorded and no account balance changes.
- Closing a period never modifies existing transactions or balances.
- The closed state of any period can be queried on the ledger, including periods that were never closed (which report `false`).

### Required public API

```java
// in com.yanimetaxas.bookkeeping.Ledger  (new methods)
void closePeriod(String period);            // period formatted as yyyy-MM
boolean isPeriodClosed(String period);
List<String> getClosedPeriods();

// new type in com.yanimetaxas.bookkeeping.exception
public class PeriodClosedException extends BusinessException
```

The exception must expose the offending period through the constructor
`PeriodClosedException(String period)`.

### Acceptance criteria

1. With the ledger's current period closed, committing an otherwise valid transfer throws `PeriodClosedException`.
2. After such a rejection, no transaction was recorded and no balance changed.
3. With no period closed, the same transfer is accepted and behaves exactly as before this requirement.
4. Closing a period does not change any existing transaction or balance.
5. `isPeriodClosed` returns `true` for a closed period and `false` for a period that was never closed.
6. `getClosedPeriods` lists exactly the closed periods.
7. Behaviour is identical on every storage backend — extend the existing cross-backend contract test to cover this.

## 中文说明（不给 Agent）

**业务场景**：会计期末结账。账期一旦关闭，就不再接受该期间的过账，避免历史期间被事后篡改。

**为什么这条需求特别有价值**：它要求引入**新的、需要持久化的状态**（哪些期间已关闭）。
在 A 上，状态放哪里、怎么存、内存与 JDBC 两套后端怎么各存一份 —— 都会直接暴露双后端实现的成本。
同时它依赖 ledger 的 `Clock`，而 A 的 `StorageProvider` 用的是「最近打开的 session」这种隐式状态，
新能力要拿到正确的时钟与账本上下文，会暴露隐式会话带来的额外耦合。

**依赖关系**：本需求依赖 R1 已引入的账户扩展点（`AccountService` 新增方法）所处的同一批扩展位置，
因此累积到第 2 轮时，A 的改动面已明显大于 B。

## 预期架构敏感点（不给 Agent）

| A 的弱点 | 预期在 A 上放大的成本 |
|---|---|
| `transferFunds` / `storeTransaction` 双后端实现 | 「当前期间是否关闭」的判断要在两处后端各加一次 |
| `StorageProvider` 隐式会话状态 | 新能力要拿到账本时钟与状态，被迫依赖隐式 session |
| 无持久化状态的统一抽象 | 「已关闭期间」这一新状态在 memory/jdbc 两套 schema 里各建一份 |
| `Ledger` God Facade | 三个新方法挂在 301 行门面上 |
