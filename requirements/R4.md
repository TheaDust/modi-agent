# R4 · Actor on postings, and per-account posting history

## Agent-facing spec

### Business requirement

A transfer may identify **who initiated it** — an actor, such as a user id or a service name.

- The actor is optional. A transfer committed without an actor behaves exactly as before this requirement, and its posting simply carries no actor.
- When an actor is supplied, it is recorded on the resulting posting and can be read back.
- The ledger can list the postings of a given account. Each listed posting reports the transaction reference, the transaction type, the timestamp, and the actor (`null` when none was supplied).
- The actor is part of the stored posting: it survives a reload from any storage backend and is returned identically.
- Recording an actor never changes the amounts, the balances or the number of postings.

### Required public API

```java
// in com.yanimetaxas.bookkeeping.model.TransactionRequest / TransferRequest
public String getActor();

// in com.yanimetaxas.bookkeeping.model.Transaction
public String getActor();

// new type in com.yanimetaxas.bookkeeping.model
public final class AccountPosting {
    public AccountPosting(String transactionRef, String transactionType, Money amount, String actor, Instant timestamp);
    public String getTransactionRef();
    public String getTransactionType();
    public Money getAmount();
    public String getActor();
    public Instant getTimestamp();
}
```

```java
// new type in com.yanimetaxas.bookkeeping.service
public interface PostingHistoryService {
    List<AccountPosting> listPostings(String accountRef);
}
```

The history service must be reachable from a ledger and must return the postings of that ledger only.

The transfer request must additionally accept an actor. The existing staged builder must keep working
exactly as before for callers that do not supply an actor — an actor may be supplied at any point after the
amount has been given, and an actor that was never supplied reads back as `null`.

### Acceptance criteria

1. A transfer committed with an actor produces a posting whose actor equals the supplied value.
2. A transfer committed without an actor produces a posting whose actor is `null`, and the transfer still succeeds exactly as before.
3. `listPostings` for an account returns one posting per transfer that touched that account, in commit order, each carrying the correct reference, type, amount and actor.
4. `listPostings` for an account that was never touched returns an empty list.
5. The actor survives a reload from storage: after reopening the ledger against the same backend, `listPostings` still reports the same actors.
6. Recording an actor does not change any balance.
7. Behaviour is identical on every storage backend — extend the existing cross-backend contract test to cover this.

## 中文说明（不给 Agent）

**业务场景**：审计追溯 —— 每一笔记账是谁做的。当前 A 的 `Transaction` 只有 reference / type / 时间戳，**没有操作者**，
所以「谁记的账」这个信息在系统里根本不存在。这是典型的「可修改性」问题：
**信息没有被建模，后续想加审计就要改动存储 schema、DTO、两套后端的映射**。

**为什么这条需求特别有价值**：它要求新增一个**需要持久化的字段**。
在 A 上，字段要加到 `Transaction`（model）、`TransactionRequest`、内存版的存储结构、JDBC 版的表结构与映射 —— 每处都是一处改动；
且 model ↔ validation / model ↔ report 已成环，新增字段容易把环加深。

## 预期架构敏感点（不给 Agent）

| A 的弱点 | 预期在 A 上放大的成本 |
|---|---|
| `Transaction` 双后端映射（内存结构 + JDBC schema/mapper） | 新字段要加到 2 套存储表示 + 2 套映射 |
| `model ↔ report` / `model ↔ validation` 循环 | 新结果类型 `AccountPosting` 放哪都会牵扯这两个环 |
| `TransferRequest` 分阶段 Builder（public 接口） | 加 actor 要动一串 public 接口，且不能破坏既有调用方式 |
| `getTransactionRefsForAccount` 等查询规则双后端实现 | 历史查询要接线两套后端 |
