# R3 · Reconciliation against an external statement

## Agent-facing spec

### Business requirement

A ledger can be **reconciled** against an external statement — for example a bank statement listing the closing balance of each account.

- A reconciliation is given a set of expected balances, each mapping an account reference to an expected monetary amount, together with a reference identifying the reconciliation.
- Reconciliation compares the expected balance of each account with the ledger's current balance of that account.
- The result reports, per account: the account reference, the expected amount, the actual amount, the difference, and whether the account reconciles.
- An account that appears in the expected set but does not exist in the ledger is reported as not reconciling, with an actual amount of zero and a difference equal to the expected amount. It must not cause the reconciliation to fail with an error.
- An account whose balance differs from the expected amount does not reconcile.
- Accounts in the ledger that are absent from the expected set are not part of the result.
- The result also reports whether **all** listed accounts reconciled.
- Reconciliation is read-only: it must not create, modify or delete any transaction, account or balance.
- Reconciliation must work on every storage backend, and must reflect balances written earlier in the same ledger.

### Required public API

```java
// new type in com.yanimetaxas.bookkeeping.model
public final class ReconciliationResult {
    public ReconciliationResult(String reference);
    public ReconciliationResult addEntry(String accountRef, Money expected, Money actual);
    public List<ReconciliationEntry> getEntries();
    public boolean isFullyReconciled();
    public String getReference();
}

public final class ReconciliationEntry {
    public String getAccountRef();
    public Money getExpected();
    public Money getActual();
    public Money getDifference();
    public boolean isReconciled();
}
```

```java
// new type in com.yanimetaxas.bookkeeping.service
public interface ReconciliationService {
    ReconciliationResult reconcile(String reference, Map<String, Money> expectedBalances);
}
```

The reconciliation service must be reachable from a ledger. The way it is obtained (constructor, factory or accessor) is free, but it must be available for a ledger backed by any storage backend, and it must observe that ledger's current balances.

### Acceptance criteria

1. A reconciliation whose expected balances all match the ledger's balances reports every entry as reconciled and the result as fully reconciled.
2. A reconciliation with one mismatching account reports that entry as not reconciled, with a difference equal to `expected − actual`, and the result as not fully reconciled.
3. An expected account that does not exist in the ledger is reported as not reconciling, with actual amount zero — and the reconciliation completes without throwing.
4. Accounts absent from the expected set do not appear in the result entries.
5. Running a reconciliation does not change any balance and does not add any transaction — verifiable by comparing balances and transaction counts before and after.
6. Reconciliation reflects balances written earlier in the same ledger.
7. Behaviour is identical on every storage backend.

## 中文说明（不给 Agent）

**业务场景**：月末与银行对账 —— 拿银行流水里的期末余额和账本余额逐户比对，找出差异。

**为什么这条需求特别有价值**：这是一个**读路径**的新能力。
在 A 上，它需要拿到「账本的当前余额」，而 A 的余额计算逻辑（`getAccountBalance`）同样在 memory/jdbc
两套后端各实现一遍，且新能力还要决定放在 `report` 包（而 `report` 与 `model` 已经成环）还是 `service` 包。
A 组必须同时在两个后端接线，B 组则可能只在一个位置接线。

## 预期架构敏感点（不给 Agent）

| A 的弱点 | 预期在 A 上放大的成本 |
|---|---|
| `getAccountBalance` 双后端实现 | 取余额的入口要在两套后端各接线一次 |
| `model ↔ report` 循环依赖 | 新结果类型放 `model` 还是 `report` 都会加深或绕开这个环 |
| `StorageProvider` 隐式会话 | 新服务要从 ledger 拿到当前会话才能读余额 |
| 无"报表/查询"统一抽象 | `report` 包只有 `LedgerReport`/`TrialBalanceReport` 两个具体类，扩展方式不明确 |
