# R1 · Per-account single-transfer debit cap

## Agent-facing spec

### Business requirement

An account may carry an optional **cap** on the total debit amount that may be posted to it within a single transfer.

- The cap is a monetary amount expressed in the account's own currency. It is supplied when the account is created and cannot be changed afterwards.
- An account created without a cap is unlimited.
- When a transfer is committed, for every account the transfer touches, the cap is evaluated as follows: take the absolute amounts of that account's **debit** legs within this transfer, add them up, and compare the sum with the account's cap. If the sum is greater than the cap, the **whole transfer** is rejected.
- A debit leg is a leg whose accounting side is `DEBIT` (see `TransactionLeg.getSide()`).
- When several legs of one transfer touch the same account, the cap is evaluated on the sum of that account's debit legs — not per leg.
- The cap is evaluated per account, not per transfer: a transfer may touch several accounts, each with its own cap.
- A rejected transfer must leave no trace: no transaction is recorded and no account balance changes.

### Required public API

Add the following to the existing public API. Existing members keep their current behaviour.

```java
// in com.yanimetaxas.bookkeeping.service.AccountService  (new overload + new method)
void createAccount(String accountRef, Money amount, AccountSide normalBalance, Money transferLimit);
Money getTransferLimit(String accountRef);   // returns null when the account has no cap

// new type in com.yanimetaxas.bookkeeping.exception
public class TransferLimitExceededException extends BusinessException
```

The exception must expose the offending account reference and the evaluated sum (both as `String`), through
constructors `TransferLimitExceededException(String accountRef, String attemptedAmount)` and
`TransferLimitExceededException(String accountRef, String attemptedAmount, String limit)`.

### Acceptance criteria

1. Committing a transfer whose debit sum for a capped account exceeds that account's cap throws `TransferLimitExceededException`.
2. After such a rejection, the account balance is unchanged and no transaction was recorded.
3. A transfer whose debit sum for an account equals that account's cap exactly is accepted.
4. An account created without a cap accepts a transfer of any size.
5. With two debit legs on the same account in one transfer, the cap is evaluated on their summed absolute amounts.
6. The cap is evaluated independently per account: one account exceeding its cap rejects the transfer even when another touched account is well within its own cap.
7. `getTransferLimit` returns the configured cap, and `null` for an account created without one.
8. Behaviour is identical on every storage backend — extend the existing cross-backend contract test to cover this.
9. When no account in the ledger has a cap, behaviour is exactly as before this requirement.

## 中文说明（不给 Agent）

**业务场景**：现金/银行科目常见的「单笔支取上限」。会计语义上，`debit` 在本项目中**减少**存储余额（见 `AccountSide` 的 javadoc），因此 debit 上限即"单笔流出上限"。

**为什么这条需求特别有价值**：账户与转账逻辑在 A 中被 `memory` 与 `jdbc` 两个后端**各实现一遍**（`createAccount`、`transferFunds` 等共 21 条规则）。在 A 上加限额校验 = **两个后端各改一次**，且两处写法不同、极易漏改；契约测试会立刻抓到不一致。在 B 上，若限额规则被收敛到单一处，则只需改一处。

## 预期架构敏感点（不给 Agent）

| A 的弱点 | 预期在 A 上放大的成本 |
|---|---|
| `transferFunds` 双后端实现 | 限额校验需在 2 处后端实现中各加一次 |
| 校验耦合 DAO（`TransferValidatorImpl` → `dao`） | 限额判断需要账户信息，被迫依赖持久化接口 |
| `Account` 与 `AccountSide` 语义耦合 | 限额是账户属性，`model` 已与 `validation` 成环，新增字段易加深循环 |
| `Ledger` God Facade | 新 API 可能需要挂到门面，进一步增大门面 |
