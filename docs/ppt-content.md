**我们做了什么**

用 Agent 对真实软件完成一次可修改性架构优化，并通过累积需求链验证这次改造的结构收益。

## 1. 为什么选这个记账库？

- **问题**　业务规则分布在多个存储后端，需求一变，多个地方可能需要一起改。提前调整架构，能减缓重复规则的累积吗？这笔投入能回本吗？
- **基线**　开源复式记账库 `double-entry-bookkeeping-api`，支持内存和 JDBC。
- **选型依据**　**62** 个 Java 主源码文件，**23** 个测试类，**182** 个测试用例通过。

依据见[基线选型记录](../benchmarks/bookkeeping/selection.md)。

## 2. 一次架构改造，把共用规则集中到业务层

**主图**　[原版 A₀ 与优化版 B₀ 同页对照 SVG](figures/ppt/architecture-comparison.drawio.svg)

**定位**　 Agent 沿调用链识别两个后端重复实现的规则。

应用的可修改性战术：

- **抽象公共服务（Abstract Common Services）**　把内存与 JDBC 后端共用的规则提取为共享实现。转账主流程通过 `AbstractTransferService` 复用，R5 预算检查可在共享流程中接入一次。
- **保持语义一致性（Maintain Semantic Coherence）**　按职责归置会一起变化的逻辑。账户规则集中在 `AccountServiceImpl`，转账规则集中在共享转账服务，具体读写由各后端负责。
- **使用封装（Use Encapsulation）**　通过 `AccountStore` 和 `TransferStore` 隐藏存储细节。端口由业务层定义、后端适配器实现，体现依赖倒置。

**即时效果**　有效多后端重复规则 **12 → 8**，近重复实现对 **5 → 0**，原有 **182** 个测试通过。

术语依据 [SEI《Modifiability Tactics》§6](https://insights.sei.cmu.edu/documents/778/2007_005_001_14858.pdf#page=21)。实际改造见[实验报告](results.md)。

## 3. 固定两个起点，比较三对完整需求链

**主图**　[三对完整链与 30 次需求实现 SVG](figures/ppt/paired-experiment.drawio.svg)

| 三项优化假设               | 怎么观察                                                             |
| -------------------------- | -------------------------------------------------------------------- |
| **H1：影响面更小**   | 同一需求下，B 触及的包更少，变更规模更小。看包数、文件数和新增行数。 |
| **H2：实现成本更低** | 同一需求下，B 的实现成本更低。看累计 token 和估算模型费用。          |
| **H3：架构劣化更慢** | 随着需求累积，B 的重复规则增加得更慢。看两组 R0–R5 的结构轨迹。     |

**3 对完整链 × 每对 2 条链 × 每链 5 个需求 = 30 次实现。**

**R1–R5 需求图例**

| 轮次                             | 业务需求                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------ |
| **R1 · 单笔借方限额**     | 每个账户可设单笔借方限额。本次转账中该账户的借方合计超限时，拒绝整笔转账。     |
| **R2 · 会计期间关闭**     | 支持关闭和查询会计期间。当前期间已关闭时，拒绝提交转账。                       |
| **R3 · 外部余额对账**     | 逐账户核对外部对账单与账本余额，报告差额和一致性。                             |
| **R4 · 操作者与记账历史** | 持久化转账操作者，并支持按账户查询记账历史。                                   |
| **R5 · 会计期间预算**     | 按账户和期间设置预算。计入本次转账后，期间累计借方金额超预算时，拒绝整笔转账。 |

- **起点与记法**　`A₀` 是上游原版，`B₀` 是 `A₀` 加一次可修改性优化，两组链各只共用这一份起点。`Aᵢ` / `Bᵢ` 是累积实现 R1…Rᵢ 后的版本，上标 k = 1, 2, 3 是第 k 次重复。
- **累积实现**　每轮从本链上一轮的产物继续。
- **配对比较**　同轮共享模型配置、需求和实现提示词。逐轮有 15 个配对，累计按 3 对完整链比较。
- **正确性门槛**　两组统一执行契约测试与冻结验收。

依据见[实验设计](experiment-design.md)和[需求规格](../benchmarks/bookkeeping/requirements/README.md)。

## 4. 优化版的重复规则累积得更慢

**主图**　[R0–R5 重复规则累积曲线 SVG](figures/ppt/structure-trend.svg)

- **主结果**　有效多后端重复规则数的中位数，A **12 → 20**，B **8 → 9**，两组中位数之差从 **4** 扩大到 **11**。
- **重复性**　3 对完整链方向一致，15 个逐轮配对中 B 的重复规则数均更低。
- **影响面**　B 在 **9/15** 个逐轮配对中触及更少的包，在 **10/15** 中新增更少的行，在 **3/15** 中改动更少的文件。
- **验收**　**30/30** 次需求实现最终通过项目测试和冻结验收。

影响面明细可放[备份页 SVG](figures/ppt/change-impact.svg)。

## 6. 三对链的实现费用有升有降，五轮内尚未回本

**主图**　[五轮实现费用与一次性架构投入 SVG](figures/ppt/five-round-cost.svg)

## 7. 结构收益重现，成本收益仍待验证

- **影响面更小**　成立。包数和新增行数偏向 B，文件数结果较混合。
- **实现成本更低**　证据不足。三对方向不一，五轮内尚未收回一次性优化费用。
- **架构劣化更慢**　成立。三对链都观察到优化版的重复规则累积更慢。

**项目贡献**　用 Agent 完成一次架构优化，并通过三对累积需求链验证这次改造的结构收益。

**结论范围**　一个记账库、一份优化起点 B₀、五项累积需求。三对实验共用同一份 B₀。
