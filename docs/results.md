# 结果：R1–R5 的 A/B 配对实验（N=3）

> 本文报告 `docs/experiment-design.md` 所述实验的实测结果。
> `python tools/results.py` 汇总现存产物，`python tools/results.py --json out.json` 导出机器可读结果。
> 每一轮的产物在 `results/<run-id>/`，清单见 `benchmarks/bookkeeping/runs.json`，索引见文末。
>
> **状态**：第一案例（记账库）R1–R5 已跑完，**N=3**（每个格子 3 个样本，A/B 各 3 条链，共 30 轮）。
> 第二案例（cron-utils）尚未进入需求轮次。

## 0. 摘要

在记账库的三对 R1–R5 累积实现中，共用同一份优化起点的 B 链，业务规则在多个存储后端重复实现的数量增加得更慢。该指标的中位数在 A 链从 12 增至 20，在 B 链从 8 增至 9。三对完整链都复现了这个方向。实现成本的方向随重复而变，计入一次架构改造的模型费用后，五轮内三对均未回本。

| 指标 | A 链（原版） | B 链（优化版） | 观察结果 |
|---|---|---|---|
| 有效多后端重复规则数 | 12 → **20** | 8 → **9** | 两组中位数差距 4 → 11，15/15 个逐轮配对 B 更低 |
| 近重复实现对数 | 5 → **7** | 0 → **0** | 15/15 个逐轮配对 B 更低 |
| 包间依赖边 | 40 → **41** | 39 → **39** | 15/15 个逐轮配对 B 更低 |
| 每轮触及包数中位数 | 8 / 5 / 3 / 5 / 7 | 6 / 5 / 3 / 4 / 5 | 9/15 个逐轮配对 B 更低 |
| 累计净改动文件数中位数 | 55 | 60 | B 累计触及更多文件 |
| 每条链累计 token（k=1/2/3） | 38.68M / 42.51M / 45.57M | 42.95M / 40.79M / 41.18M | 配对相对差 +11.1% / −4.0% / −9.6% |
| 正确性 | 15/15 次最终通过 | 15/15 次最终通过 | 两组均通过项目测试和冻结验收 |

结构指标的箭头表示从起点到 R5 的变化，终点取各组中位数。逐轮配对数用于描述方向，完整链的重复次数为 N=3。

## 1. 读懂结果所需的前提

### 1.1 记法

| 记法 | 含义 |
|---|---|
| `A_0` | 上游原版（`benchmarks/bookkeeping/source/`，上游 `imetaxas/double-entry-bookkeeping-api`，MIT） |
| `B_0` | `A_0` + 可修改性优化（三对链共用的架构改造，99 次请求 / 2211s / $0.146 / 15 文件 +791 −469） |
| `A_i^k` | A 链第 k 次重复，累积实现 R1..R_i 后的版本 |
| `B_i^k` | B 链第 k 次重复，累积实现 R1..R_i 后的版本 |

- 字母 A = 原版轨迹，B = 优化版轨迹；下标 i = 累积实现的轮次；**上标 k = 重复序号（k ∈ {1,2,3}）**。
- 每个 (轮次 i, 轨迹) 格子有 3 个样本，汇总报**中位数**并给出全距。
- **逐轮比较**按同一需求 i 和重复编号 k 配对。**累计比较**以完整 A/B 链为单位。
  k=1 的对应轮次均错开执行，k=2、k=3 的对应轮次均有时间重叠。
- `A_0` 与 `B_0` 各只有一份，被 3 次重复共用 —— 重复的是「从基线出发实现 R1…R5」这件事。
- 完整定义见 `docs/experiment-design.md` §5。

### 1.2 自变量与控制变量

实验处理是**起点版本**（`A_0` 或 `B_0`）。以下配置和产物记录均已对 30 轮核验。

| 控制项 | 本次实测（30 轮逐轮核对） |
|---|---|
| 系统提示词 | 30 轮 `systemPromptSha256` **只有一个取值**（`1059379fdf1c…`）—— 与 N=1 批次同一份 |

## 2. 执行过程：前因后果

这一节记录实验执行中实际发生的问题与处置。每一条都影响数据可用性，故完整留档。

### 2.1 编排脚本自身的缺陷（已修正）

首次编排四轮时，运行函数同时把进度字符串写进了输出流，导致 `$rounds[0].runDir` 取到字符串而非对象，
于是 C2 的 `--from` 变成 `"/workspace"`（未真正执行），D2 的 `--from` 误指向 C1 的工作副本。

**后果**：C2、D2 两轮作废（D2 是在错误起点上跑的 R2）。D1 同批因传输层错误崩溃。
**处置**：函数只写文件、不写输出流，并在缺 `runDir` 时跳过 R2 轮次。
最终批次使用重跑产物。
**留下的教训**：人工编排靠"复制上一轮的路径字符串"传参极易出错。这直接催生了 §2.5 的链编排器。

### 2.2 传输层失败：自动重试的引入

D1 在第 56 次请求后以 `stopReason: error` / `Connection error.` 崩溃。四轮里挂了两轮。

**诊断**：网关（`opencode.ai/zen`）的瞬时传输错误，与实现质量无关。
**处置**：`agent/runtime.mjs` 开启 `retry: { enabled: true, provider: { maxRetries: 3 } }`。
**为什么必须开**：不重试会**随机淘汰某一组的某一轮** —— 这既浪费样本，也给配对比较注入与自变量无关的噪声。
重试上限对两组一致，属于「运行环境」而非自变量。
最终 30 轮采用相同的传输重试配置。编排记录显示，扩样批次的 20 轮均于首次编排尝试完成。

### 2.3 守卫一刀切造成的组间偏差（本实验最关键的方法论修正）

C1 连续两轮被判无效，违规均为 `public-api-removed`：
`InMemoryAccountDao.createAccount(String, String, Money, AccountSide)` 的四参版本消失。

**核对源码确认是真阳性**：A 组把四参方法**直接改成五参**（加上 `transferLimit`），而不是新增重载；
B 组则**保留四参版本并新增五参重载**，两者共用一个私有 `store(...)`。

**表面处理**：给 `prompts/feature.md` 加一条「新增能力一律以新增成员加入，不得替换既有 public 方法签名」。

**但这个处理本身是错的**，理由有三：

1. **需求根本没规定 DAO 的签名。** 实验设计的铁律是「规定对外 API，但不规定实现位置、模块归属与设计模式」，
   DAO 方法签名属于实现自由度。要求保留签名，等于偷偷加了一条需求里没有的约束。
2. **冻结验收与既有契约测试都不依赖那个签名。** 核实结果：冻结验收用例只调门面 API
   （`ledger.accountService().createAccount(...)`）；既有测试里**确有**直接引用 DAO 类的用例
   （`InMemoryDaoEdgeTest` 直接构造 `InMemoryAccountDao` 并调 `updateBalance`/`getAccounts`，
   `JdbcStorageDetailsTest` 调 `validator.setAccountDao(...)`），但**没有任何一个测试调用
   `createAccount`**。因此替换该签名既不会让既有测试编译或断言失败（与 C1 那轮 220 例全绿一致），
   也不影响冻结验收 —— 行为等价验证与两组可比性都不受影响。
3. **最要命的是抽样偏差。** A 组没有端口接缝 → agent 自然去改 DAO 签名 → 守卫判无效 → 重跑 →
   **A 组的有效样本被条件化在「agent 恰好想到了加重载」**；B 组有端口 → 自然加重载 → 通过，
   **无条件化**。于是 A 的有效样本是「筛过的」，B 的是「全体」，二者不再可比。
   这与被测构念（架构是否影响可修改性）毫无关系。

**处置**：把一条规则拆成三级（`docs/experiment-design.md` §2）：

| 级别 | 情形 | 判定 |
|---|---|---|
| 一级 | **需求规定**的 public 类型或方法被删改 | **判无效**（冻结验收编不过 → 行为等价无法验证） |
| 二级 | 需求**未规定**的 public 类型或方法被**删除**（功能消失） | **判无效**（「删功能换 diff 变小」是真实作弊通道） |
| 三级 | 需求**未规定**的 public 方法**签名被替换**（功能保留） | **不判无效，记入指标** |

`bench/guard.py` 据此把 API 差分拆为 `removedTypes`/`removedMethods`（二级，判违规）与
`changedSignatures`（三级，记录于 `api.changedSignatures`，不判违规）。实现上按方法名分组即可区分：
若 after 侧存在**同名**方法则为替换，否则才是删除。

**对结论的影响**：三级判定让「破坏公共 API 的概率」成为一个**可测指标**而非淘汰机制。
N=3 的 30 轮里该指标共出现 2 次（见 §3.1 末），**没有一轮因此被判废，也没有损失样本**。
这正是三级判定相对一刀切的全部收益。

### 2.4 冻结验收用例自身的两处缺陷（已订正）

早期验收发现 R4 和 R5 各有一处用例缺陷。

**缺陷一（R4）**：`R4AcceptanceTest.postingsAreListedPerAccountInSubmissionOrder` 断言
`getTransactionType()` 等于 `"sale"`，而同文件使用的辅助方法 `AcceptanceSupport.payment(...)`
提交的交易类型固定为 `"payout"` —— **用例与自己的辅助方法自相矛盾**。两组都正确返回了实际提交的
`"payout"`，反被判失败。已订正为 `"payout"`。

**缺陷二（R5）**：`R5AcceptanceTest.budgetsAreCheckedPerAccount` 提交了一笔借记 `REVENUE` 500.00 的转账，
而该用例账本里 `REVENUE` 余额为 0.00，于是被项目**原有**的余额校验
（`TransferValidatorImpl.validBalance` → `InsufficientFundsException`）先行拒绝，
**根本走不到预算逻辑** —— 任何实现都不可能通过。已给该用例的收入账户补足资金
（`AcceptanceSupport` 增加带收入余额的重载），断言与需求意图均未改动。

**处置**：订正判据后**只重判、不重跑 Agent**（Agent 产物未变，重新判定即可）；
原始判定留档为 `acceptance.orig.json`。订正只改判据、不改需求、不偏向任何一组。

最终批次的 30 轮均按订正后的判据通过。保留的 k=1 原始验收文件显示，R4 两组均已通过，R5 两组各有 1 个失败，订正后重新验收通过。

### 2.5 从 N=1 扩到 N=3：链编排器

首批链由人工编排。扩样使用 `bench/chain.mjs`，把起点选择、失败处理和过程记录固定在同一流程中。

- **链内严格串行**：第 i 轮的起点由编排器从上一轮**成功产出**的工作副本读出，不靠人工传参。
- **失败即丢弃、链条位置不动**：某轮若 Agent 中断、被守卫判废、既有测试或冻结验收不过，
  该轮产物作废并**重跑同一轮**（起点仍是上一轮的成功产物）；连续 3 次失败才中止整条链。
  判定表见 `bench/chain.mjs` 的 `classify`，有单元测试覆盖（`test/chain.test.mjs`，6 例）。
- **状态落盘**：每次尝试的判定、token 与验收结果写入 `results/_chains/<链名>/state.json`，
  逐轮日志留在同目录，可断点续跑、事后核对。
- **链间并行**：扩样批次四条链同时启动，k=2 和 k=3 各自的 A/B 对应轮次均有时间重叠。

编排器记录了新增 20 轮各一次尝试。最终报告汇总这 20 轮及首批 10 轮的最终验收结果。

**公共方法签名替换（守卫第三级）：30 轮共记录 2 次。**

| 轮次 | 变化 | 兼容性 |
|---|---|---|
| `A_1^3` | `InMemoryAccountDao.createAccount` 4 参 → 只剩 5 参 | **无兼容重载**，旧调用方直接编译不过 |
| `B_1^2` | `InMemoryAccountDao.createAccount` 3 参 → 3 参+limit 与 4 参并存 | **端口层兼容**：端口把原 3 参改成 `default` 方法转发 `null`，但适配器类自身的 3 参重载消失 |

R2–R5 的 24 轮全部为 0。**两组在此维度打平（各 1 次）**，
不构成"B 更少破坏契约"的证据 —— N=1 时两者都是 0，无法区分。

> **这个指标有一处粗粒度，值得记下来**：`changedSignatures` 把上面两种情况算成同一种（各记 1 次），
> 但它们的**兼容性后果不同**（一个完全无替代，一个在端口层保住了兼容）。
> 2 个样本也不足以估计发生率。若要继续用这个指标，应先把"是否存在向后兼容的替代重载"拆成独立字段。

**有效多后端重复规则数**是本项目的核心架构指标（对应的可视化见图 3：
`docs/figures/degradation-curve.drawio.png`）：它按「这条规则是否在多个存储后端各实现一遍」计数，

**B 链不是完全免疫，只是幅度小得多**：B_2^3 / B_3^3 / B_4^3 / B_5^3 达到 9，B_5^2 达到 11。
对应的是需求 R2（关账）与 R5（预算）—— B 的这些轮次里 agent 确实在两个后端各写了一遍，
但数量级远小于 A 链同样轮次的增量。

**层级违规与依赖边要分开说**：

- **包间依赖边**：B 链 15 个版本恒为 39，A 链从 40 涨到 41（R5 有 2/3 的重复增加了 1 条边）。
  15/15 配对 B 更优。
- **层级违规**：**两组基本无差异**。A 链中位数全程为 1，R5 按 k=1/2/3 分别为 2 / 1 / 1。

## 4. 讨论

### 4.1 共享规则改变了新增需求的落点

`B_0` 把账户规则、转账规则和会话初始化分别收敛到 `AccountServiceImpl`、`AbstractTransferService` 和 `AbstractStorageProvider`，并通过 `AccountStore`、`TransferStore` 让具体存储实现提供所需的读写操作。A 链沿用多个存储后端分别实现规则的结构。到 R5，三条 A 链的有效重复规则分别增加 8、8、9 条，三条 B 链分别增加 0、3、1 条。B 链仍有部分规则在多个后端各自实现。

共享抽象也带来了新增接口。R5 的 public 方法数中位数为 A **312**、B **326**，近重复方法对数的中位数为 A **7**、B **0**。同时报告这两项可以看到，优化后的接口规模增大，而实现重复减少。

### 4.2 结构变化如何影响实现成本

共享规则可能减少重复实现需要的工作，额外的抽象也可能增加理解和接线的开销。持久化需求还会带来各后端各自承担的表结构、内存布局与数据转换工作。当前记录汇总了整轮用量，无法量化这几部分各占多少。五轮内观测到的结构差异，比模型费用差异有更一致的方向。

## 5. 局限

| 局限 | 对结论的影响 |
|---|---|
| 三对完整链共用一份 `A_0` 和一份 `B_0` | 重复检验的是后续需求实现。实验只覆盖这一次优化产物 |
| 链内轮次相依，且各轮需求不同 | 15 个逐轮配对用于描述方向。累计成本以三个完整链对比较 |
| 执行时段和模型波动 | k=1 的对应轮次错开，扩样批次并行。网关负载未直接测量 |
| 单个项目和一组预先设计的需求 | 结果适用于本记账库、这份优化版本及所测变化场景 |
| 测试覆盖与 API 差分粒度 | 冻结验收以业务语义为主。两次签名替换的兼容性后果仍需结合源码判断 |
| 验收和守卫曾订正 | 最终结果统一采用订正后的口径。历史判定和改动原因见 §2 |

---

## 6. 结论

在这个记账库中，三对完整链都显示：从同一份优化版出发，跨后端重复规则累积得更慢。五轮后的中位数为 A **20**、B **9**，两组均通过项目测试和冻结验收。实现成本在三次重复中方向不一。按日志估算模型费用并计入一次优化，在本实验的五轮范围内，三对 B 链均未达到费用持平。

## 7. 复现步骤

```powershell
# 0. 前置：Node.js 24+、本机 Maven、.env 已配置模型与 MAVEN_PATH
npm run agent:check

# 1. 生成 B_0（架构优化）：工作副本落在 results/<id>/workspace
npm run agent -- --benchmark bookkeeping --mode optimize

# 2. 生成 4 条链（k=2,3；k=1 见 benchmarks/bookkeeping/runs.json）
node --env-file=.env bench/chain.mjs --side A --replicate 2 --base benchmarks/bookkeeping/source

node --env-file=.env bench/chain.mjs --side B --replicate 3 --base results/<B_0 的 id>/workspace

# 3. 事后统计（全部分析；--json 导出机器可读结果）
python tools/results.py
python tools/results.py --json out.json
```

每轮的产物：`run.json`（来源与提示词哈希）、`summary.json`（成本）、`diff.json`（变更规模）、
`guard.json`（反作弊与 API 差分）、`verification.json`（既有测试）、`acceptance.json`（冻结验收）、
`events.jsonl`（逐回合事件与 token）、`workspace/`（工作副本，含起点基线提交）。
