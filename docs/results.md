# 结果：R1–R5 的 A/B 配对实验（N=3）

> 本文是 `docs/experiment-design.md` 方法论对应的实测结果。所有数字都能由本仓库的脚本复现：
> `python tools/results.py` 打印全部分析，`python tools/results.py --json out.json` 导出机器可读结果。
> 每一轮的产物在 `results/<run-id>/`，清单见 `benchmarks/bookkeeping/runs.json`，索引见文末。
>
> **状态**：第一案例（记账库）R1–R5 已跑完，**N=3**（每个格子 3 个样本，A/B 各 3 条链，共 30 轮）。
> 第二案例（cron-utils）尚未进入需求轮次。

## 0. 摘要

架构级预先投资把「加一条业务规则要改几处」从**随轮次增长**压成了**近似常数** —— 这一条在
**15/15 个配对**上成立。但「预先投资能省下实现成本」这一条，**不成立**：成本差异落在噪声里。

| 指标 | A 链（原版轨迹） | B 链（优化版轨迹） | 判定 |
|---|---|---|---|
| **有效多后端重复规则数**（= 加一条规则要改几处） | 12 → **20**（中位） | 8 → **8–9**（中位） | **15/15 配对 B 更优**，差距 4 → 12 |
| 原始同名规则计数 | 21 → **32** | 17 → **24** | **15/15 配对 B 更优** |
| 近重复实现对数 | 5 → **7**（最高 12） | 0 → **0** | **15/15 配对 B 更优** |
| 包间依赖边 | 40 → **41** | 39 → **39** | **15/15 配对 B 更优** |
| 触及包数（单轮） | 8 / 5 / 3 / 5 / 7 | 6 / 5 / 3 / 4 / 5 | 9/15 配对 B 更优，方向一致但强度弱 |
| 累计净改动文件数 | 55（中位） | **60（中位）** | **反向信号**：B 的改动更碎，A 的更集中 |
| 实现成本（累计 token） | 38.68M / 42.51M / 45.57M | 42.95M / 40.79M / 41.18M | **中位 B 便宜 4.0%**，15 配对里 8 比 7 —— **无系统差异** |
| 层级违规数 | 1 → **1**（R5 最高 2） | 1 → **1** | 两组基本无差异（1/15 配对 B 更优） |
| 正确性 | 既有测试与冻结验收**全绿** | 同左 | **行为等价** |

**一句话结论**：**收益确凿地体现在结构上，不体现在成本上。**
B 链把「每加一条规则要改几处」钉在 8 条附近（A 链从 12 涨到 20），四个结构指标在 15 个配对上
**无一例外**地偏向 B；但实现成本上，B 链中位数比 A 链**低 4.0%**（k=1 时曾测得高 11.1%），
15 个单轮配对里 B 便宜 8 个、贵 7 个 —— **先前那条「B 更贵」是单样本噪声，现已被证伪**。

> **这一版相对 N=1 的三处结论修正**（都是扩大样本后原结论没有复现）：
> 1. **成本**：N=1 报「B 累计贵 11.1%，差距单调收窄但未交叉」；N=3 的中位是**B 便宜 4.0%**，
>    且 k=1 那条链恰是 3 个样本里唯一 B 更贵的一条。H2 应判为**不成立**。
> 2. **「A_5 侵蚀分层」**：N=1 报「A 链 R5 新增 1 个层级违规 + 1 条依赖边」；N=3 显示
>    层级违规在 3 个重复里是 **1 / 2 / 1**（中位 1，与 A_0 相同），依赖边 41 / 41 / 40。
>    「R5 侵蚀分层」只在 1/3 的重复里出现，**不能作为趋势陈述**。
> 3. **「B 链五轮从未多于 A 链」（触及包数）**：N=3 下 9/15 配对 B 更优，R2 与 R3 各 0/3。
>    方向仍偏向 B，但**不再是"从未"**。

## 1. 读懂结果所需的前提

### 1.1 记法

| 记法 | 含义 |
|---|---|
| `A_0` | 上游原版（`benchmarks/bookkeeping/source/`，上游 `imetaxas/double-entry-bookkeeping-api`，MIT） |
| `B_0` | `A_0` + 可修改性优化（**唯一一次**架构改造，99 次请求 / 2211s / $0.146 / 15 文件 +791 −469） |
| `A_i^k` | A 链第 k 次重复，累积实现 R1..R_i 后的版本 |
| `B_i^k` | B 链第 k 次重复，累积实现 R1..R_i 后的版本 |

- 字母 A = 原版轨迹，B = 优化版轨迹；下标 i = 累积实现的轮次；**上标 k = 重复序号（k ∈ {1,2,3}）**。
- 每个 (轮次 i, 轨迹) 格子有 3 个样本，汇总报**中位数**并给出全距。
- **配对单位是 (i, k)**：`A_i^k` 与 `B_i^k` 配成一对。同一 k 的两条链**并行执行**，
  于是配对同时控住了需求难度与网关负载的时间漂移。
- `A_0` 与 `B_0` 各只有一份，被 3 次重复共用 —— 重复的是「从基线出发实现 R1…R5」这件事。
- 完整定义见 `docs/experiment-design.md` §5。

### 1.2 自变量与控制变量

唯一自变量是**起点版本**（`A_0` vs `B_0`）。其余全部钉死，且已对**全部 30 轮**逐项核验：

| 控制项 | 本次实测（30 轮逐轮核对） |
|---|---|
| 系统提示词 | 30 轮 `systemPromptSha256` **只有一个取值**（`1059379fdf1c…`）—— 与 N=1 批次同一份 |
| 需求文本 | 每一轮 6 个样本（A/B × 3 次重复）的 `promptSha256` **唯一**：R1 `2e97c4a4…`、R2 `b400bc64…`、R3 `82e8f13c…`、R4 `6527ebe7…`、R5 `2a396b49…` |
| 模型 / 温度 / 思考等级 / 上下文窗口 | `deepseek-v4.1-flash` / temperature=0 / medium / 512000，30 轮一致 |
| 工具集与权限 | 7 个工具（read/grep/find/ls/edit/write/powershell），30 轮一致 |
| 重试策略 | 开启，`maxRetries=3`，30 轮一致（见 §2.2） |
| 累积关系 | 每轮起点 = 上一轮**成功产出**的工作副本，24 条链内衔接全部核对通过（由编排器保证，见 §2.5） |
| 冻结验收用例数 | 每一轮 6 个样本完全相同（7 → 11 → 16 → 21 → 27），实现方自写用例数不同但不影响判据 |
| 两边包集合 | `A_0` 与 `B_0` 的 Java 包集合完全相同（各 12 个），"触及包数"的分母一致 |

> **提示词一致性是扩样的前提**：N=1 批次跑完后 `prompts/feature.md` 又被改过一次。
> 若第 1 条链用的是旧版、新跑的 20 轮用新版，第 1 条链就不是同条件的样本，N=3 会是个假 N。
> 核对结果是当前文件的 sha256 = `1059379fdf1c…`，**与那 10 轮记录的 `systemPromptSha256` 逐位相同**，
> 因此第 1 条链可直接当 k=1 使用。

### 1.3 为什么最终只看三个指标

空间有限，最终只展示三个槽位。选择依据不是「哪个更重要」，而是它们构成**机制 → 结果 → 代价**
的完整链条：

| 槽位 | 指标 | 对应假设 | 为什么是它 |
|---|---|---|---|
| ① | 变更规模与影响面 | H1 | 「同样的契约，改动更小」是核心主张 |
| ② | 实现成本 | H2 | **唯一不依赖 diff 大小**的指标，能排除「代码本来就短」这个竞争性解释 |
| ③ | 多后端重复实现的业务规则数 | H3 + 归因 | 给出**机制**：为什么 B 更便宜。而非「这次运气好」 |

**正确性不进这三个名额**：H4 是二元判定，两组全绿就是全绿，一行交代即可。
但它保护的是上面三个指标的**全部合法性** —— 等价性一破，三组数字都不可比。

## 2. 执行过程：前因后果

这一节记录实验执行中实际发生的问题与处置。每一条都影响数据可用性，故完整留档。

### 2.1 编排脚本自身的缺陷（已修正）

首次编排四轮时，运行函数同时把进度字符串写进了输出流，导致 `$rounds[0].runDir` 取到字符串而非对象，
于是 C2 的 `--from` 变成 `"/workspace"`（未真正执行），D2 的 `--from` 误指向 C1 的工作副本。

**后果**：C2、D2 两轮作废（D2 是在错误起点上跑的 R2）。D1 同批因传输层错误崩溃。
**处置**：函数只写文件、不写输出流，并在缺 `runDir` 时跳过 R2 轮次。
**对结论的影响**：无 —— 作废轮次全部丢弃，最终批次重跑。
**留下的教训**：人工编排靠"复制上一轮的路径字符串"传参极易出错。这直接催生了 §2.5 的链编排器。

### 2.2 传输层失败：自动重试的引入

D1 在第 56 次请求后以 `stopReason: error` / `Connection error.` 崩溃。四轮里挂了两轮。

**诊断**：网关（`opencode.ai/zen`）的瞬时传输错误，与实现质量无关。
**处置**：`agent/runtime.mjs` 开启 `retry: { enabled: true, provider: { maxRetries: 3 } }`。
**为什么必须开**：不重试会**随机淘汰某一组的某一轮** —— 这既浪费样本，也给配对比较注入与自变量无关的噪声。
重试上限对两组一致，属于「运行环境」而非自变量。
**对结论的影响**：无偏；改善的是样本留存率。N=3 的 30 轮全部一次通过，无一轮需要重试。

### 2.3 守卫一刀切造成的组间偏差（本实验最关键的方法论修正）

C1 连续两轮被判无效，违规均为 `public-api-removed`：
`InMemoryAccountDao.createAccount(String, String, Money, AccountSide)` 的四参版本消失。

**核对源码确认是真阳性**：A 组把四参方法**直接改成五参**（加上 `transferLimit`），而不是新增重载；
B 组则**保留四参版本并新增五参重载**，两者共用一个私有 `store(...)`。

**表面处理**：给 `prompts/feature.md` 加一条「新增能力一律以新增成员加入，不得替换既有 public 方法签名」。

**但这个处理本身是错的**，理由有三：

1. **需求根本没规定 DAO 的签名。** 实验设计的铁律是「规定对外 API，但不规定实现位置、模块归属与设计模式」，
   DAO 方法签名属于实现自由度。要求保留签名，等于偷偷加了一条需求里没有的约束。
2. **冻结验收与既有契约测试都不依赖那个签名。** 核实结果：冻结验收用例只调门面 API
   （`ledger.accountService().createAccount(...)`）；既有测试里**确有**直接引用 DAO 类的用例
   （`InMemoryDaoEdgeTest` 直接构造 `InMemoryAccountDao` 并调 `updateBalance`/`getAccounts`，
   `JdbcStorageDetailsTest` 调 `validator.setAccountDao(...)`），但**没有任何一个测试调用
   `createAccount`**。因此替换该签名既不会让既有测试编译或断言失败（与 C1 那轮 220 例全绿一致），
   也不影响冻结验收 —— 行为等价验证与两组可比性都不受影响。
3. **最要命的是抽样偏差。** A 组没有端口接缝 → agent 自然去改 DAO 签名 → 守卫判无效 → 重跑 →
   **A 组的有效样本被条件化在「agent 恰好想到了加重载」**；B 组有端口 → 自然加重载 → 通过，
   **无条件化**。于是 A 的有效样本是「筛过的」，B 的是「全体」，二者不再可比。
   这与被测构念（架构是否影响可修改性）毫无关系。

**处置**：把一条规则拆成三级（`docs/experiment-design.md` §2）：

| 级别 | 情形 | 判定 |
|---|---|---|
| 一级 | **需求规定**的 public 类型或方法被删改 | **判无效**（冻结验收编不过 → 行为等价无法验证） |
| 二级 | 需求**未规定**的 public 类型或方法被**删除**（功能消失） | **判无效**（「删功能换 diff 变小」是真实作弊通道） |
| 三级 | 需求**未规定**的 public 方法**签名被替换**（功能保留） | **不判无效，记入指标** |

`bench/guard.py` 据此把 API 差分拆为 `removedTypes`/`removedMethods`（二级，判违规）与
`changedSignatures`（三级，记录于 `api.changedSignatures`，不判违规）。实现上按方法名分组即可区分：
若 after 侧存在**同名**方法则为替换，否则才是删除。

**对结论的影响**：三级判定让「破坏公共 API 的概率」成为一个**可测指标**而非淘汰机制。
N=3 的 30 轮里该指标共出现 2 次（见 §3.1 末），**没有一轮因此被判废，也没有损失样本**。
这正是三级判定相对一刀切的全部收益。

### 2.4 冻结验收用例自身的两处缺陷（已订正）

R4、R5 轮退出码为 3（冻结验收未通过），但**A 组与 B 组完全同因失败**，指向判据本身。

**缺陷一（R4）**：`R4AcceptanceTest.postingsAreListedPerAccountInSubmissionOrder` 断言
`getTransactionType()` 等于 `"sale"`，而同文件使用的辅助方法 `AcceptanceSupport.payment(...)`
提交的交易类型固定为 `"payout"` —— **用例与自己的辅助方法自相矛盾**。两组都正确返回了实际提交的
`"payout"`，反被判失败。已订正为 `"payout"`。

**缺陷二（R5）**：`R5AcceptanceTest.budgetsAreCheckedPerAccount` 提交了一笔借记 `REVENUE` 500.00 的转账，
而该用例账本里 `REVENUE` 余额为 0.00，于是被项目**原有**的余额校验
（`TransferValidatorImpl.validBalance` → `InsufficientFundsException`）先行拒绝，
**根本走不到预算逻辑** —— 任何实现都不可能通过。已给该用例的收入账户补足资金
（`AcceptanceSupport` 增加带收入余额的重载），断言与需求意图均未改动。

**处置**：订正判据后**只重判、不重跑 Agent**（Agent 产物未变，重新判定即可）；
原始判定留档为 `acceptance.orig.json`。订正只改判据、不改需求、不偏向任何一组。

**对结论的影响**：无偏；两组在同一判据下都通过。N=3 的 30 轮冻结验收**全部一次通过**，
说明订正后的判据没有引入新的误判。

### 2.5 从 N=1 扩到 N=3：链编排器

N=1 的四轮靠人工编排（§2.1 的教训），且 §2.3 的抽样偏差说明**"判废后重跑"这件事必须由程序按固定语义执行**，
否则每条链的起点会被人工传参带偏。N=3 之前先补上 `bench/chain.mjs`：

- **链内严格串行**：第 i 轮的起点由编排器从上一轮**成功产出**的工作副本读出，不靠人工传参。
- **失败即丢弃、链条位置不动**：某轮若 Agent 中断、被守卫判废、既有测试或冻结验收不过，
  该轮产物作废并**重跑同一轮**（起点仍是上一轮的成功产物）；连续 3 次失败才中止整条链。
  判定表见 `bench/chain.mjs` 的 `classify`，有单元测试覆盖（`test/chain.test.mjs`，6 例）。
- **状态落盘**：每次尝试的判定、token 与验收结果写入 `results/_chains/<链名>/state.json`，
  逐轮日志留在同目录，可断点续跑、事后核对。
- **链间并行**：4 条链同时跑，同一 k 的 A/B 链并行，使配对两侧面对相同的网关负载条件。

**首轮即 30/30 一次通过**：没有一轮需要重跑，说明三级判定 + 重试 + 判据订正之后，
编排链路本身是稳定的。

### 2.6 已丢弃的轮次

本次实验共产生 **35 个运行目录**，其中 **31 个保留**（30 个实验轮次 + `B_0`），**4 个已清理**。
被丢弃的构成：

| 类别 | 数量 | 说明 |
|---|---|---|
| `npm run agent:smoke` 的测试残留 | 3 | `cron-utils-inspect`、`bookkeeping-feature`、`bookkeeping-optimize` 各一 |
| 早期 `bench:test` 残留 | 1 | `baseline-cov` |

**保留的 `B_0`**（`2026-11-20T08-41-49-404Z-bookkeeping-optimize-3d81d743`）是 B 链全部 15 轮的
`--from` 来源，删除会切断整条链。

## 3. 结果

### 3.1 槽位① 变更规模与影响面（H1）

单轮指标（3 样本中位数 `[全距]`）：

| 轮次 | 侧 | 触及包数 | 文件数 | 新增行 | 删除行 |
|---|---|---|---|---|---|
| R1 | A | 8 [7, 8] | 21 [21, 22] | 450 [408, 472] | 15 [15, 20] |
| R1 | B | **6** [6, 7] | 20 [20, 22] | 481 [359, 603] | 23 [15, 24] |
| R2 | A | 5 [4, 5] | 22 [21, 23] | 566 [532, 809] | 11 [7, 17] |
| R2 | B | 5 [5, 6] | 24 [23, 30] | 538 [498, 574] | 2 [2, 16] |
| R3 | A | 3 | 7 [7, 8] | 653 [552, 690] | 0 |
| R3 | B | 3 | 7 [7, 8] | 494 [347, 496] | 0 |
| R4 | A | 5 | 17 [16, 18] | 586 [526, 620] | 16 [10, 26] |
| R4 | B | **4** | 17 [16, 19] | 538 [492, 607] | 12 [11, 22] |
| R5 | A | 7 [6, 7] | 27 [25, 28] | 1189 [970, 1272] | 6 [6, 24] |
| R5 | B | **5** [5, 6] | 28 [28, 29] | 1216 [946, 1220] | 18 [10, 22] |

**配对统计（15 个 (轮次, 重复) 配对，负值 = B 更小）**：

| 指标 | 中位差 | 全距 | B 更优 |
|---|---|---|---|
| 触及包数 | **−1** | [−2, +2] | 9/15 (60%) |
| 新增行数 | **−34** | [−311, +195] | 10/15 (67%) |
| 文件数 | 0 | [−2, +9] | **3/15 (20%)** |

**判定：方向成立，强度弱于 N=1 的读数。**

- **触及包数仍是本槽位最干净的表达**：B 更优的配对集中在 R1（3/3）、R4（3/3）、R5（3/3），
  而 R2（0/3）、R3（0/3）打平。全距 [−2, +2] 说明单轮优势在 0–2 个包之间，不是压倒性的。
- **文件数这个口径是反的**（B 更优仅 3/15）。原因与 §4.4 相同：A 的「双份实现」是平行且局部的
  （照现有模式复制），B 的「单份实现」需要动抽象层 + 适配器 + 接线，**波及的文件更多但每个更短**。
- **行数口径不可用作主口径**：R5 的新增行 B 反而多 27 行（1216 vs 1189），
  因为 B 的单份实现要跨抽象层接线，A 的双份实现是各写各的。

**累计净变更（链的起点 → R5 末，`git diff --no-index --numstat`）**：

| 链 | 改动文件数 | 新增行 | 删除行 |
|---|---|---|---|
| `A^1` | 57 | 3280 | 55 |
| `A^2` | 55 | 3774 | 38 |
| `A^3` | 46 | 3217 | 56 |
| `B^1` | 56 | 3092 | 40 |
| `B^2` | 60 | 3149 | 54 |
| `B^3` | 66 | 3145 | 60 |

**这一项是个反向信号，必须写出来**：B 的累计改动**文件数中位数 60 高于 A 的 55**，
但**新增行中位数 3145 略低于 A 的 3280**。即 B 的改动更碎（更多、更小的文件），
A 的改动更集中（更少、更大的文件）。这与单轮的「文件数反向、行数同向」是同一件事的两个尺度，
也解释了为什么槽位① 只有触及包数这个口径能用。

**公共 API 破坏性变更（三级判定的第三级）：30 轮共 2 次。**

| 轮次 | 变化 | 兼容性 |
|---|---|---|
| `A_1^3` | `InMemoryAccountDao.createAccount` 4 参 → 只剩 5 参 | **无兼容重载**，旧调用方直接编译不过 |
| `B_1^2` | `InMemoryAccountDao.createAccount` 3 参 → 3 参+limit 与 4 参并存 | **端口层兼容**：端口把原 3 参改成 `default` 方法转发 `null`，但适配器类自身的 3 参重载消失 |

R2–R5 的 24 轮全部为 0。**两组在此维度打平（各 1 次）**，
不构成"B 更少破坏契约"的证据 —— N=1 时两者都是 0，无法区分。

> **这个指标有一处粗粒度，值得记下来**：`changedSignatures` 把上面两种情况算成同一种（各记 1 次），
> 但它们的**兼容性后果不同**（一个完全无替代，一个在端口层保住了兼容）。
> 2 个样本也不足以估计发生率。若要继续用这个指标，应先把"是否存在向后兼容的替代重载"拆成独立字段。

> 它说明**在 token 口径下**，这类投资的收益体现在返工成本与债务累积上，
> 而这个实验的五轮窗口还不足以让债务充分显现。

## 4. 讨论：为什么会出现这些结果

**4.1 机制是清楚的。** B_0 的优化把「账户规则」「转账/记账规则」「会话前导」分别收敛到
`AccountServiceImpl`、`AbstractTransferService`、`AbstractStorageProvider`，并用 `AccountStore` /
`TransferStore` 两个窄端口把存储原语留在 memory / jdbc 适配器里。此后每加一条规则，
agent 面对的是一个**单一接缝** —— 所以 B 链 15 个版本里只有 5 个偏离了 8 这个数。
A_0 没有这个接缝，agent 只能照着既有模式在两个后端各写一遍，于是规则数随轮次累积。

**4.2 为什么成本上没有差异。** 三条原因叠加：

1. **必要重复成本摊薄了差距**（实验设计 §3.6）。表结构、内存布局、模型↔存储转换属于必要的存储差异，
   两组都要付；R4、R5 这类「新增持久化字段」的需求中这部分占比最高。
2. **两组都要写测试**。既有测试数在 214–413 之间波动，是实现方自写用例的主要来源，
   与架构无关。`prompts/feature.md` 要求"优先扩展既有的跨实现共享契约测试"，
   但 agent 实际写多少仍由实现难度驱动，架构债只影响其中一部分。
3. **B 的固定成本与 A 的债务成本恰好抵消**。B 要先读懂多出的抽象层（输入 token 与缓存读取系统性更高），
   A 要多写一份实现（输出 token 与重复测试更高）。两边都在涨，涨幅相当。

**4.3 为什么"行数"和"文件数"两个口径都不可靠。** 行的数量反映"这次写了多少字"，文件数反映"这次动了几处"，
两者都与「波及多广」只有弱相关。真正与可修改性直接对应的量纲是**触及包数**与**「要改几处」**。
B 的单份实现需要动抽象层 + 适配器 + 接线，**文件更多但每个更短**；
A 的双份实现是平行且局部的，**文件更少但每个更长**。这是同一件事的两面。
累计净变更把这个对比推到了极端：B 的累计改动**文件数中位 60 > A 的 55**，
新增行中位 3145 < A 的 3280 —— **B 的改动更碎，A 的改动更集中**。
如果只看文件数或只看行数，会得到相反的结论，所以槽位① 的主口径只能是触及包数。

**4.4 差异不是"代码更少"。** B_5 的 public 方法数 320 附近，高于 A_5 的 312 附近；
B 的 public 类型里有 5 个是 `B_0` 引入的共享抽象。
**B 的近重复方法对数全程为 0**，A 链从 5 涨到 7（`A_5^3` 甚至到 12）。
B 赢在"规则只有一处"，不是"代码更少"。

**4.5 关于样本量的一个方法论收获。** 本实验最重要的修正是 §2.3 的三级判定 —— 它防的是**抽样偏差**。
但 N=1→N=3 暴露的是另一类问题：**单样本的极端值会被读成"趋势"**。
k=1 那条链在成本上恰好是 3 个样本里唯一 B 更贵的一条，而它的累计曲线（+32.1% → +19.1% → +12.3% → +11.1%）
**单调收窄**，看上去像一条教科书式的趋势 —— 完全是巧合。
**任何一条"单调"曲线在 N=1 下都可能是运气。** 这是把 N 从 1 提到 3 最大的价值。

## 5. 局限与有效性威胁

| 威胁 | 程度 | 说明与缓解 |
|---|---|---|
| **N=3 仍然偏小** | **高** | 每格 3 个样本。成本指标尤其不稳：R1 的 B 组全距 6.10M–12.40M（2 倍）。结论只能表述为"方向"与"未发现系统差异"，**不能声称成本等价** |
| **成本指标本身噪声大** | **高** | 15 个配对里 8 比 7，接近抛硬币。H2 判为"不成立"的准确含义是**没有检出差异**，不是"证明了相同" |
| **单一项目过拟合** | 中 | 结论限定于本案例的架构风格；cron-utils 的需求轮次尚未开展 |
| **需求对架构敏感是设计出来的** | 中 | R1–R5 刻意落在 A_0 的已知弱点上。需求对两组完全一致、只讲业务行为不讲代码结构 |
| **必要重复成本摊薄差距** | 中 | 表结构、内存布局、模型↔存储转换、事务策略两组都要付（§4.2）。它会**摊薄**组间差距，R4/R5 尤其明显 |
| **"触及包数"的口径依赖包结构** | 低 | 两边包集合完全一致（各 12 个），分母无差异；但该指标把「同一模块内的多个文件」算作一个包，粒度较粗 |
| **`changedSignatures` 粒度粗** | 低 | 把"无兼容替代"与"端口层用 default 方法保住兼容"算成同一种（§3.1 末）。2 个样本不足以估计发生率 |
| **B 被「教会」** | 低 | 优化提示词只给变化**类别**（新增实现 / 新增校验 / 新增查询 / 新增字段），不含业务内容；工作副本中无需求文档，agent 读不到 R1–R5 |
| **守卫判据曾随观测调整** | 低 | 已在 §2.3 记录调整的**理由、时点与方向**；调整方向是**放宽**（签名替换不再判废）且对两组对称，方向上不利于原假设 |
| **冻结验收用例曾订正** | 低 | 两处均为用例自身缺陷，两组同因失败，订正后两组同时通过（§2.4） |

## 6. 结论

1. **架构级预先投资确实把「加一条业务规则要改几处」压成了近似常数。**
   四个结构指标在 **15/15 个配对**上无一例外地偏向 B：有效多后端重复规则数（−8）、
   原始同名计数（−6）、近重复方法对数（−7）、包间依赖边（−1）。
   A 链中位数 12 → 20，B 链 8 → 8–9，**差距从 4 扩大到 12**。

2. **成本上没有测到收益。** 累计 B−A = +11.1% / −4.0% / −9.6%，**中位 −4.0%**，
   15 个单轮配对里 B 便宜 8 个、贵 7 个。H2 判为**不成立**。
   早先基于 N=1 的「B 更贵 11.1%、差距单调收窄」是单样本噪声，现予修正。

3. **收益的性质是「劣化被阻断」，不是「单轮更便宜」。** B 链的近重复实现对数全程为 0，
   A 链从 5 涨到 7；B 的依赖边恒为 39，A 涨到 41。预先投资买到的是**返工面**，
   而这个实验的五轮窗口还不足以让 A 链的债务在 token 上显形。

4. **正确性无差异**：30 轮既有测试与冻结验收全绿，两组行为等价。

**下一步**：① 把 N 提到 5 以上，只为把成本指标的分辨率提上来（结构指标在 N=3 已经饱和）；
② 开展第二案例（cron-utils）的需求轮次以检验外部效度；
③ 把 `changedSignatures` 拆成「是否留有向后兼容的替代重载」两个字段。

```powershell
npm run agent:check

# 1. 生成 B_0（架构优化）：工作副本落在 results/<id>/workspace
npm run agent -- --benchmark bookkeeping --mode optimize

# 2. 生成 4 条链（k=2,3；k=1 见 benchmarks/bookkeeping/runs.json）
node --env-file=.env bench/chain.mjs --side A --replicate 2 --base benchmarks/bookkeeping/source
node --env-file=.env bench/chain.mjs --side B --replicate 2 --base results/<B_0 的 id>/workspace
node --env-file=.env bench/chain.mjs --side A --replicate 3 --base benchmarks/bookkeeping/source
node --env-file=.env bench/chain.mjs --side B --replicate 3 --base results/<B_0 的 id>/workspace

# 3. 事后统计（全部分析；--json 导出机器可读结果）
python tools/results.py
python tools/results.py --json out.json
```

每轮的产物：`run.json`（来源与提示词哈希）、`summary.json`（成本）、`diff.json`（变更规模）、
`guard.json`（反作弊与 API 差分）、`verification.json`（既有测试）、`acceptance.json`（冻结验收）、
`events.jsonl`（逐回合事件与 token）、`workspace/`（工作副本，含起点基线提交）。
