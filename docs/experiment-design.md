# 实验设计：对可修改性的架构级预先投资能否降低后续变更成本

> 本文是作业的方法论主体。所有结论必须能由本仓库的脚本、配置与原始日志复现。

---

## 1. 研究问题与假设

**RQ1（核心）** 对可修改性做架构层面的**预先投资**，能否显著降低后续需求变更的实现成本？

**RQ2** 该收益是否随需求轮次累积而**放大**（架构劣化曲线发散），而不是一次性现象？

**RQ3** 收益具体体现在哪些可观测维度（影响面 / 规模 / 成本 / 架构指标）？

| 假设 | 表述 | 判定方式 |
|---|---|---|
| **H1** | 在同一新需求下，`diff(B→D)` 的变更规模与影响面显著小于 `diff(A→C)` | 配对比较（每轮一组 A/B 配对），中位数 + 效应量 |
| **H2** | B 组的实现成本（LLM 调用次数 / token / 货币成本 / 墙钟时间）低于 A 组 | 同上 |
| **H3** | 随轮次累积，两组的变更成本曲线**发散** | 逐轮指标序列的可视化 + 趋势检验 |
| **H4** | 两组在正确性上无差异（B/C/D 均通过同一套契约测试） | 契约测试全绿，二元判定 |

## 2. 自变量与控制变量

**唯一自变量**：起点代码版本（`A` = 上游原版 vs `B` = 可修改性优化版）。

其余全部钉死，任何一项在两组间不一致，实验即失效：

| 控制项 | 钉死方式 |
|---|---|
| Agent 实现 | 同一份代码、同一版本 tag（`agent/` 目录） |
| 底层模型 | 同一模型 ID、temperature、思考等级与输出 token 上限；由 `.env` 配置并保存脱敏快照 |
| 系统提示词 | 同一份 `prompts/feature.md`，仅需求文本段落不同 |
| **对外 API 契约** | **需求文件规定要新增的 public 类型与方法，两组完全一致**（见下方说明） |
| 工具集与权限 | 同一份 `agent/runtime.mjs` 与 Pi SDK 1.2.0；需求实现两组启用相同工具与权限 |
| 上下文策略 | 同一历史裁剪策略、同一上下文窗口 |
| 测试与验收 | 同一 `mvn test` 命令、同一验收判据 |
| 工作目录 | 等价的独立 git worktree，互不污染 |

#### 共享提示词（`prompts/feature.md`）的内容与边界

该提示词是两组唯一的任务指导，逐字相同。它只允许包含**对两组对称**的工作规范，不允许出现
任何指向某一种架构形态的指示，否则自变量被污染，结论无法归因到架构。

| 条款 | 为什么必须写进提示词 |
|---|---|
| 公共 API 逐字对齐、不得另造替代入口 | 若两组 API 本身不同，diff 不可比、行为等价无法自动验证 |
| 不得跳过/禁用/删除测试、不得写死特判 | `bench/guard.py` 只能检出断言变更与测试删除，检不出"让构建变绿"的规避手法 |
| 不得借需求之机提取、合并或重写既有实现为新共享抽象 | 这是最关键的一条：若 A 组在 R1 就顺手做了架构优化，两组差距从第一轮起就被抹平，`diff(A→C)` 不再代表"在原版上实现需求的成本" |
| 优先扩展既有的跨实现共享契约测试，而非为单个实现各写一套 | 否则两组的测试代码量天然不等，`linesAdded` 与 token 成本会被测试代码而非实现难度主导 |
| 优先复用既有扩展点，无则按项目现有风格实现 | 通用且对称：A 组没有共享机制就会按自身风格实现，B 组有共享机制就会复用——这正是"可修改性预先投资"要测的传导路径 |
| 不得提问或等待澄清，须自行判断并推进 | 运行是非交互的；停在提问处会得到一个未完成的空回合 |
| 完整测试套件全绿后才结束，并如实报告 | `verification.json` 与 `acceptance.json` 才能区分"实现正确"与"Agent 自证" |

> **不得写进提示词的内容**（会破坏实验）："把规则只实现一次"、"抽一个抽象基类"、
> "消除多后端重复实现"、"让校验不依赖持久化接口"等指向 B 的架构形态的指示；
> 以及 R1–R5 的业务内容、阈值与场景细节。
> 若希望 B 表现更好，正确的杠杆是 `prompts/optimize.md`（只作用于 B 的生产环节），
> 而不是两组共享的 `prompts/feature.md`。

#### 为什么必须规定对外 API

本项目 A 是**库**，对外契约就是 Java 公共 API。若放任 agent 自由设计 API：

1. A 组与 B 组会做出**不同的 API** → `diff` 无法对比（比的是两套不同功能的实现，不是同一功能的两种实现）；
2. 行为等价**无法自动验证**（没有共同的可调用面，就写不出跨组通用的验收测试）；
3. 「差异」将同时包含「API 设计差异」与「架构差异」——**构念效度被破坏**，结论无法归因到架构。

因此每个需求规定 **业务行为 + public API 表面**，但**不规定实现位置、模块归属与设计模式**。
这样两组做的是**同一个契约的两种实现**，可测量的差异只剩下「代码放在哪、怎么组织、波及多大」——
这正是本实验要测的东西。

| 规定 | 不规定 |
|---|---|
| 新增哪些 public 类型、方法及其语义 | 放在哪个模块、哪个包 |
| 异常类型名与构造参数 | 用不用策略模式、要不要抽接口 |
| 行为与验收标准 | 是否复用既有抽象、是否新增扩展点 |

### 关键的反作弊约束（必须同时用提示词与事后 diff 双重保障）

1. **禁止在实现新需求时顺手做架构级重构。** 否则 A 组也会边改需求边重构，两组差距被稀释成噪声。
   - 提示词层：`prompts/feature.md` 明确禁止移动/重命名/拆分既有类、禁止改变既有模块依赖方向。
   - 事后层：`bench/guard.py` 检测需求实现 diff 中是否出现「既有类被删除/移动」「非目标模块的包结构变化」，命中即标记该轮实验**无效**并重跑。
2. **禁止修改既有测试的断言。** 契约测试是行为等价性的判据，改断言等于改判据。
   - 事后层：diff 中 `src/test/**` 的**断言行**发生变化即判无效（允许新增测试文件/用例）。
3. **禁止删功能换 diff 变小。** 以契约测试全绿 + 需求验收测试通过为准。

## 3. 因变量（指标体系）

只报 "diff 行数" 会被质疑「你只是让代码变短了」。因此用 **4 类代理指标** 共同刻画：

### 3.1 变更影响面（Impact）
- 触及文件数 `files_changed`
- 触及的包 / 模块数 `packages_touched`
- 跨模块依赖变更条数 `cross_module_edges_delta`（依赖图 diff）
- 新增 / 删除的 public API 签名数（用于「向后兼容」核查）

### 3.2 变更规模（Size）
- `git diff --numstat` 的新增行、删除行、修改文件数

### 3.3 变更成本（Cost）
- LLM 调用轮数 `llm_calls`
- 输入 / 输出 token（含缓存命中）
- 货币成本 `cost_usd`（按 `.env` 中的 `MODEL_COST_*` 单价与 token 用量估算）
- 墙钟时间 `wall_time_s`
- 工具调用次数与失败重试次数

> 成本指标的价值在于：它**不依赖 diff 的大小**，能排除「代码本来就短」这一竞争性解释。

### 3.4 架构质量（Structure）
由 `tools/structure.py` 自动计算（对 A/B/C/D 逐一运行，输出可对比的 JSON）：

| 指标 | A 基线 | B 目标 |
|---|---|---|
| 包间循环依赖数（强连通分量） | 2 | 0 |
| 层级违规数（业务包 → 持久化包） | 1 | 0 |
| **多后端重复实现的业务规则数**（有效计数，排除平凡 getter 与纯委派） | **12**（原始同名计数 21） | 不增加；残留项逐条说明必要差异 |
| 近重复实现对数（token 相似度 ≥ 0.45） | 5 | ≤ 1 |
| 包间依赖边数 | 40 | ≤ 40（不靠「减少功能」来降） |
| public 类型 / 方法数 | 58 / 242 | B 不减；C/D 只允许新增 |

> **「多后端重复实现的业务规则数」是本项目最核心的架构指标**：
> 它直接对应「加一条业务规则要改几处」。内存版与 JDBC 版代码写法必然不同（Map 与 SQL），
> 因此 token 相似度会低估风险；本指标按**规则是否在多个后端各实现一遍**来计数，不看写法。
> `tools/structure.py` 同时输出原始同名计数与有效计数：后者保守地排除平凡 getter 和
> `super./delegate.` 纯委派，只有至少两个后端仍有实质实现时才计入。两者都只作**诊断指标**，
> 不单独作为 B 的验收门限——B 的门限是契约测试全绿、无破坏性 public API 变更、
> 结构指标不恶化，以及残留重复项逐条说明必要差异。

### 3.5 正确性（Correctness）
- 契约测试（5 个存储后端）全绿
- 新需求的验收测试全绿

> **已处理的局限**：验收标准仍要求实现方「扩展现有跨后端契约测试」，因此 `verification.json`
> 的全绿只证明「Agent 自写的测试通过」。为此另备 `benchmarks/bookkeeping/acceptance/` 下
> 由实验方冻结的 R1–R5 验收用例，运行前临时复制进工作副本、单独跑一遍 `mvn test`，
> 结果写入 `acceptance.json`；该文件在跑完后立即删除，不污染工作副本与 diff。
> 两组结果分列报告，以区分「实现正确」与「Agent 自证」。
> 冻结用例只验证业务语义（内存后端）；跨后端一致性仍依赖实现方自写的契约测试，这一残余局限在报告中声明。

### 3.6 必要重复成本（解释变量）
一部分变更成本无论 A、B 都一样，属于**必要的存储差异**，不是架构债：
表结构与内存布局（schema / 内存结构各一份）、模型到存储表示的转换、事务与锁策略。
R4、R5 这类「新增持久化字段」的需求中，这部分成本占比最高，会**摊薄**架构差异。
报告时须把「可消除的重复成本」与「必要重复成本」分开陈述，避免把差距不足全部归因于架构无效。

## 4. 行为等价性的保障机制

这是本实验的**地基**，没有它整个对比无效。

项目 A 自带跨后端契约测试（`LedgerContractTest` 的 5 个实现：InMemory / H2 / Derby / HSQL / SQLite）。这套测试：

1. 在 A 上**原样固化**；
2. 在 B / C / D 上**逐字复制**后运行；
3. 任一后端的行为漂移 → 判定该版本行为不等价 → 实验作废。

同时，「对外接口向后兼容」用**public API 签名差分**核查（B 相对 A 不得有破坏性变更；C/D 相对其基线只允许新增）。

## 5. 版本与 diff 的组织（git 原生）

每个案例的代码放在 `benchmarks/<案例名>/source/`；例如记账库为 `benchmarks/bookkeeping/source/`，
cron-utils 为 `benchmarks/cron-utils/source/`。A/B 表示同一案例的原版与优化版。
以下以单个案例为例，用**分支**表达实验版本，使 `git diff` 本身就是指标来源：

```
main              → A          上游原版
b/optimized       → B          A + 可修改性优化（唯一一次架构改造）
c/r1              → C1         A + 需求 R1
d/r1              → D1         B + 需求 R1
c/r2              → C2         A + 需求 R2   （从 c/r1 递进）
d/r2              → D2         B + 需求 R2   （从 d/r1 递进）
...
```

于是：

```
diff(A,  C) = git diff main..c/rN
diff(B,  D) = git diff b/optimized..d/rN
diff(A,  B) = git diff main..b/optimized     ← 架构改造的规模
```

每轮 agent 的运行在**独立 git worktree** 中进行，互不干扰，且任何一轮都可单独复现。

## 6. 有效性威胁

| 威胁 | 缓解措施 |
|---|---|
| **内部效度**：LLM 非确定性，单次结果可能是噪声 | 每组重复 N 次取中位数；固定模型、温度与运行环境；记录全部原始日志与 seed |
| **外部效度**：单项目，结论可能过拟合于该风格 | 结论限定表述；架构风格差异需注明；留出第二项目作为扩展 |
| **构念效度**：「可修改性」是不可直接观测的抽象构念 | 用 4 类代理指标联合刻画，并声明代理关系；辅以 QAS 把可修改性写成可测场景 |
| **统计结论效度**：样本量小 | 用配对比较 + 中位数 + 效应量；不做过度显著性声明；原始数据全部公开 |
| **需求污染**：需求描述可能暗示特定实现 | 需求文本对 A/B 完全一致；需求描述只讲业务行为，不讲代码结构 |
| **B 被「教会」**：优化提示词给出通用变化场景，等于告诉 B 未来会变什么 | 场景只给**类别**（新增一种实现 / 新增一条校验规则 / 新增一个查询 / 新增一个字段），不含任何业务内容、阈值或 API；工作副本中不含需求文档，Agent 无法读到 R1–R5；结论表述限定为「针对这些通用变化类型的预先投资」 |
| **评分者偏差**：A 与 B 谁"看起来更好" | 不做人工主观评分，全部用自动化指标 |
