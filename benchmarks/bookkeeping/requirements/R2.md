# R2 · 会计期间关闭

## 给智能体的需求

### 业务需求

每笔记账都归属于一个**会计期间**，该期间由打开账本时指定的时钟推导。期间使用 `yyyy-MM` 格式的字符串标识，例如 `2026-01`。

- 期间可以被**关闭**。关闭操作作用于账本，所有使用该账本的调用者都能观察到关闭状态。
- 账本的**当前**期间关闭时，提交转账必须被拒绝，并抛出专用异常。
- 当前期间根据尝试提交转账时的时钟确定。
- 拒绝转账后，不得留下任何交易记录，也不得改变任何账户余额。
- 关闭期间不修改已有交易或余额。
- 可以查询账本中任意期间的关闭状态；从未关闭的期间返回 `false`。

### 公共 API 要求

```java
// 在 com.yanimetaxas.bookkeeping.Ledger 中新增方法
void closePeriod(String period);            // 期间格式为 yyyy-MM
boolean isPeriodClosed(String period);
List<String> getClosedPeriods();

// 新类型所在包：com.yanimetaxas.bookkeeping.exception
public class PeriodClosedException extends BusinessException
```

异常必须通过构造方法 `PeriodClosedException(String period)` 暴露导致拒绝的期间。

### 验收标准

1. 账本当前期间关闭时，提交一笔原本有效的转账将抛出 `PeriodClosedException`。
2. 拒绝后没有新增交易记录，所有余额保持不变。
3. 未关闭任何期间时，同一笔转账能够成功，且行为与实现本需求前完全一致。
4. 关闭期间不改变任何已有交易或余额。
5. `isPeriodClosed` 对已关闭期间返回 `true`，对从未关闭的期间返回 `false`。
6. `getClosedPeriods` 列出且仅列出所有已关闭期间。
7. 所有存储后端行为一致，扩展现有跨后端契约测试以覆盖此需求。

## 中文说明（不给 Agent）

**业务场景**：会计期末结账。账期一旦关闭，就不再接受该期间的过账，避免历史期间被事后篡改。

**为什么这条需求特别有价值**：它要求引入**新的、需要持久化的状态**（哪些期间已关闭）。
在 A 上，状态放哪里、怎么存、内存与 JDBC 两套后端怎么各存一份 —— 都会直接暴露双后端实现的成本。
同时它依赖 ledger 的 `Clock`，而 A 的 `StorageProvider` 用的是「最近打开的 session」这种隐式状态，
新能力要拿到正确的时钟与账本上下文，会暴露隐式会话带来的额外耦合。

**依赖关系**：本需求依赖 R1 已引入的账户扩展点（`AccountService` 新增方法）所处的同一批扩展位置，
因此累积到第 2 轮时，A 的改动面已明显大于 B。

## 预期架构敏感点（不给 Agent）

| A 的弱点 | 预期在 A 上放大的成本 |
|---|---|
| `transferFunds` / `storeTransaction` 双后端实现 | 「当前期间是否关闭」的判断要在两处后端各加一次 |
| `StorageProvider` 隐式会话状态 | 新能力要拿到账本时钟与状态，被迫依赖隐式 session |
| 无持久化状态的统一抽象 | 「已关闭期间」这一新状态在 memory/jdbc 两套 schema 里各建一份 |
| `Ledger` 过大的门面 | 三个新方法挂在 301 行门面上 |
