# R5 · 账户会计期间预算

## 给智能体的需求

### 业务需求

账户可以为某个会计期间设置**预算**，限制该期间内所有转账记入该账户的借方累计总额。

- 预算针对一个账户和一个会计期间设置，使用该账户的币种。
- 提交转账时，根据账本当时的时钟确定当前期间，规则与关闭期间时一致。对转账涉及的每个账户，查询其在**当前期间**的预算：
  - 已设置预算时，将本次转账中该账户的借方分录合计金额加到该期间已记入的借方累计金额中；若新总额大于预算，拒绝**整笔转账**。
  - 未设置预算时，该账户在该期间不受此限制。
- 账户在某期间的已记借方金额跨转账累积。进入后续期间后，该期间的累计金额从零开始。
- 预算按账户独立检查，不按整笔转账汇总检查。
- 拒绝转账后，不得留下任何交易记录，不得改变任何账户余额，期间累计借方金额也保持不变。
- 预算属于账本状态，在所有存储后端上行为一致。

### 公共 API 要求

```java
// 新类型所在包：com.yanimetaxas.bookkeeping.service
public interface BudgetService {
    void setBudget(String accountRef, String period, Money amount);
    Money getBudget(String accountRef, String period);      // 未设置预算时返回 null
    Money getBudgetUsed(String accountRef, String period);  // 该期间已记入的借方金额
}

// 新类型所在包：com.yanimetaxas.bookkeeping.exception
public class BudgetExceededException extends BusinessException
```

异常必须通过构造方法 `BudgetExceededException(String accountRef, String period)` 暴露超限账户引用和期间。

必须能够从账本获得预算服务，服务应反映该账本的当前状态。

### 验收标准

1. 转账将使已设置预算的账户在该期间的累计借方金额超过预算时，抛出 `BudgetExceededException`。
2. 拒绝后没有新增交易，所有余额保持不变，`getBudgetUsed` 的值也保持不变。
3. 累计借方金额恰好达到预算时，允许转账。
4. 当前期间未设置预算的账户在该期间不受此限制。
5. 借方金额按期间累积：一个期间的金额不计入另一期间的预算使用量。
6. 同一转账中同一账户有多条借方分录时，先求和再检查预算。
7. 各账户独立检查预算：即使其他账户未超预算，只要一个账户超预算，就拒绝整笔转账。
8. `getBudget` 返回配置的预算，未设置时返回 `null`；`getBudgetUsed` 返回该期间的累计借方金额。
9. 所有存储后端行为一致，扩展现有跨后端契约测试以覆盖此需求。

## 中文说明（不给 Agent）

**业务场景**：项目预算控制 —— 「本月这个科目的支出上限是 X，超了就不许再记」。
这是把 R1 的「单笔限额」升级为「周期累计额度」，因此也把 R2 的「会计期间」概念真正用起来。

**为什么这条需求特别有价值**：这是**第 5 轮**需求，A 组此时已经累积了 R1–R4 的所有改动。
本需求要求**同时**用到：账户（账本上下文）、会计期间（R2 引入的状态）、期间累计金额（新的聚合查询）。
在 A 上，这三者分别散落在 memory/jdbc 两套后端、隐式 session、以及两套查询实现里；
到第 5 轮时，A 组的改动波及面会被前面几轮的架构债**放大**，而 B 组因为前几轮已经把规则收敛到单处，
本需求很可能只需在一处落地。这就是「架构劣化曲线」的拐点。

**依赖关系**：依赖 R2（会计期间）与 R1（账户扩展位）。

## 预期架构敏感点（不给 Agent）

| A 的弱点 | 预期在 A 上放大的成本 |
|---|---|
| `transferFunds` / `storeTransaction` 双后端实现 | 预算校验 + 期间累计写入，两套后端各一次 |
| 无聚合查询抽象 | 「期间累计 debit」这个新聚合要在两套后端各写一遍 SQL / Map 逻辑 |
| `StorageProvider` 隐式会话 | 取「当前期间」与「已用额度」都要走隐式 session |
| `model ↔ validation` 循环 | 预算判定属于校验规则，却被绑在 DAO 上 |
| 累积效应 | 第 5 轮的改动面 = 前 4 轮架构债 × 本需求触及的模块数 |
