# R1 · 账户单笔转账借方限额

## 给智能体的需求

### 业务需求

账户可以设置一个可选的**限额**，用于限制单次转账中记入该账户的借方总额。

- 限额使用账户自身币种，在创建账户时指定，创建后不可修改。
- 创建时未指定限额的账户不受此限制。
- 提交转账时，对转账涉及的每个账户，将本次转账中该账户各**借方**分录金额的绝对值相加，并与账户限额比较。总额大于限额时，拒绝**整笔转账**。
- 借方分录指记账方向为 `DEBIT` 的分录，参见 `TransactionLeg.getSide()`。
- 同一转账中有多条分录涉及同一账户时，按该账户借方分录的合计金额检查限额，不逐条检查。
- 限额按账户独立计算；一笔转账可以涉及多个账户，各有自己的限额。
- 拒绝转账后，不得留下任何交易记录，也不得改变任何账户余额。

### 公共 API 要求

在现有公共 API 中添加以下成员，并保持已有成员的行为。

```java
// 在 com.yanimetaxas.bookkeeping.service.AccountService 中新增重载和方法
void createAccount(String accountRef, Money amount, AccountSide normalBalance, Money transferLimit);
Money getTransferLimit(String accountRef);   // 账户未设置限额时返回 null

// 新类型所在包：com.yanimetaxas.bookkeeping.exception
public class TransferLimitExceededException extends BusinessException
```

异常必须通过构造方法 `TransferLimitExceededException(String accountRef, String attemptedAmount)` 和
`TransferLimitExceededException(String accountRef, String attemptedAmount, String limit)`
暴露超限账户的引用和本次计算的合计金额，两者均使用 `String`。

### 验收标准

1. 提交转账时，若受限账户的借方合计金额超过其限额，抛出 `TransferLimitExceededException`。
2. 拒绝后账户余额不变，且没有新增交易记录。
3. 借方合计金额恰好等于账户限额时，允许转账。
4. 未设置限额的账户接受任意金额的转账。
5. 同一转账中同一账户有两条借方分录时，按两者金额绝对值之和检查限额。
6. 各账户独立检查限额：即使其他账户未超限，只要一个账户超限，就拒绝整笔转账。
7. `getTransferLimit` 返回配置的限额；未设置时返回 `null`。
8. 所有存储后端行为一致，扩展现有跨后端契约测试以覆盖此需求。
9. 账本中所有账户均未设置限额时，行为与实现本需求前完全一致。

## 中文说明（不给 Agent）

**业务场景**：现金/银行科目常见的「单笔支取上限」。会计语义上，`debit` 在本项目中**减少**存储余额（见 `AccountSide` 的 javadoc），因此 debit 上限即"单笔流出上限"。

**为什么这条需求特别有价值**：账户与转账逻辑在 A 中被 `memory` 与 `jdbc` 两个后端**各实现一遍**（`createAccount`、`transferFunds` 等共 21 条规则）。在 A 上加限额校验 = **两个后端各改一次**，且两处写法不同、极易漏改；契约测试会立刻抓到不一致。在 B 上，若限额规则被收敛到单一处，则只需改一处。

## 预期架构敏感点（不给 Agent）

| A 的弱点 | 预期在 A 上放大的成本 |
|---|---|
| `transferFunds` 双后端实现 | 限额校验需在 2 处后端实现中各加一次 |
| 校验耦合 DAO（`TransferValidatorImpl` → `dao`） | 限额判断需要账户信息，被迫依赖持久化接口 |
| `Account` 与 `AccountSide` 语义耦合 | 限额是账户属性，`model` 已与 `validation` 成环，新增字段易加深循环 |
| `Ledger` 过大的门面 | 新 API 可能需要挂到门面，进一步增大门面 |
