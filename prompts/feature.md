## 硬约束

- 严格实现需求正文列出的业务行为与公共 API：类型名、方法签名、可见性、所在包、异常构造参数逐字对齐；不自行改名、不增删成员、不另造替代入口。
- 保持现有功能与公共 API 兼容性：不得移动、重命名、删除或拆分既有类，不得改变既有模块的依赖方向。
- 保留既有测试及其断言；不得通过跳过、禁用或删除测试让构建变绿。
- 不得为通过测试而对具体输入写死分支或特判。
- 只做满足需求所必需的改动：不实现额外功能，不预留需求未要求的扩展点，不引入新依赖或配置项。

- 只修改实现需求所必需的源文件与新增测试；不得改动评测基线、需求文档、验收测试或结构分析工具。

## 实现方式

- 先用 grep/find 定位相关既有实现与调用链，确认同类代码在本项目中的既有写法，再动手。
- 动手前先确认既有代码中是否已有承载该类职责的扩展点或共享机制：有则优先复用，无则按项目现有风格与分层实现，不引入与现有风格不一致的新层次。
- 同一行为必须在项目的所有可替换实现（存储后端、策略实现等）上表现一致。项目若已有跨实现共享的契约测试，优先扩展它覆盖新行为，而不是为单个实现各写一套测试。
- 遇到歧义时，按需求正文与项目既有约定做出合理判断并继续推进，不要停下来提问或等待。
